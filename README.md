# Техническое задание

# Task Manager — приложение для управления задачами

**Тип проекта:** Web Application\
**Уровень:** Junior / Beginner\
**Технологии:** HTML, CSS, JavaScript\
**Формат работы:** Индивидуальная практическая работа

---

# 1. Цель проекта

Необходимо разработать браузерное приложение для создания и управления списком задач.

Приложение должно позволять пользователю создавать задачи, редактировать их состояние, удалять, искать, фильтровать и сортировать.

Главная цель проекта — закрепить изученные темы JavaScript и научиться применять новые возможности языка при разработке реального приложения.

Работа должна выполняться самостоятельно. Готовые решения из интернета, сторонние библиотеки и JavaScript-фреймворки использовать нельзя.

# 2. Структура проекта

Проект должен состоять из трёх основных файлов:

- `index.html` — структура приложения.
- `style.css` — оформление приложения.
- `script.js` — логика приложения.

Допускается создание дополнительных файлов, если это необходимо для организации проекта.

# 3. Описание интерфейса

Приложение должно содержать следующие основные области.

## 3.1. Заголовок приложения

В верхней части страницы необходимо разместить:

- Название приложения.
- Краткое описание назначения приложения.
- Общее количество задач.

## 3.2. Форма создания задачи

Необходимо реализовать форму добавления новой задачи.

Форма должна содержать:

- Поле для ввода названия задачи.
- Кнопку добавления задачи.

Требования:

- Название задачи обязательно.
- Нельзя добавлять пустые задачи.
- Нельзя добавлять задачу, состоящую только из пробелов.
- После успешного добавления поле ввода должно очищаться.
- Пользователь должен получать понятную обратную связь при некорректном вводе.

## 3.3. Список задач

Основная часть приложения должна отображать все созданные задачи.

Для каждой задачи необходимо показывать:

- Название.
- Дату создания.
- Текущий статус.
- Элемент управления для изменения статуса.
- Кнопку удаления.

Внешний вид задачи должен зависеть от её статуса.

Выполненные задачи должны визуально отличаться от активных.

Если список пуст, вместо списка необходимо показывать соответствующее информационное сообщение.

## 3.4. Панель статистики

Необходимо отображать три показателя:

1. Общее количество задач.
2. Количество выполненных задач.
3. Количество активных задач.

Все показатели должны автоматически обновляться при любых изменениях списка.

Пример:

| Показатель  | Значение |
| ----------- | -------: |
| Всего задач |       10 |
| Выполнено   |        4 |
| Осталось    |        6 |

Значения в примере приведены только для иллюстрации интерфейса.

# 4. Этап №1. Организация данных и базовая логика

**Основные темы:**

- Объекты.
- Массивы.
- Функции.
- Параметры и аргументы функций.
- Возвращаемые значения.
- Операторы и условия.
- Циклы.

На первом этапе необходимо реализовать логику приложения без привязки к пользовательскому интерфейсу.

## 4.1. Организация задачи

Каждая задача должна иметь следующие характеристики:

| Свойство      | Описание                        |
| ------------- | ------------------------------- |
| ID            | Уникальный идентификатор задачи |
| Название      | Текстовое название задачи       |
| Статус        | Выполнена задача или нет        |
| Дата создания | Дата и время создания задачи    |

## 4.2. Начальные данные

При запуске логики приложения должен существовать первоначальный список из нескольких тестовых задач.

Среди них должны быть как выполненные, так и невыполненные задачи.

## 4.3. Управление задачами

Необходимо реализовать следующие возможности:

**Создание задачи**

- Получение названия новой задачи.
- Проверка корректности названия.
- Создание новой задачи.
- Добавление задачи в общий список.

**Удаление задачи**

- Удаление конкретной задачи по её идентификатору.
- Если задача отсутствует, приложение должно корректно обработать ситуацию.

**Изменение статуса**

- Изменение статуса задачи на противоположный.
- Возможность повторно изменить статус.

**Подсчёт статистики**

- Подсчёт общего количества задач.
- Подсчёт выполненных задач.
- Подсчёт активных задач.

## 4.4. Требования к функциям

Логика приложения должна быть разделена на отдельные функции.

Каждая функция должна отвечать за конкретную операцию.

Необходимо избегать ситуации, когда вся логика приложения находится в одной большой функции.

**Результат этапа:** реализована основная логика управления задачами.

# 5. Этап №2. Работа с массивами и коллекциями

**Основные темы:**

- Методы массивов.
- Поиск элементов.
- Фильтрация данных.
- Преобразование данных.
- Сортировка.
- Стрелочные функции.

На этом этапе необходимо расширить возможности обработки списка задач.

## 5.1. Поиск задачи

Реализовать возможность получения конкретной задачи по её идентификатору.

## 5.2. Фильтрация

Необходимо реализовать получение отдельных списков:

- Все задачи.
- Только активные задачи.
- Только выполненные задачи.

Фильтрация не должна изменять исходный список задач.

## 5.3. Поиск по названию

Пользователь должен иметь возможность искать задачи по названию.

Требования:

- Поиск должен учитывать часть названия.
- Поиск не должен зависеть от регистра букв.
- При отсутствии совпадений должно отображаться соответствующее сообщение.
- При очистке поискового поля должны снова отображаться все задачи с учётом выбранного фильтра.

## 5.4. Сортировка

Добавить возможность сортировки задач:

- От старых к новым.
- От новых к старым.
- По алфавиту от А до Я.
- По алфавиту от Я до А.

Сортировка не должна приводить к потере или изменению данных задач.

## 5.5. Получение дополнительной информации

Необходимо реализовать получение:

- Списка названий всех задач.
- Количества выполненных задач.
- Количества активных задач.
- Списка задач, созданных в определённый период.

**Результат этапа:** приложение умеет самостоятельно обрабатывать, искать, фильтровать и сортировать данные.

# 6. Этап №3. Работа с HTML и DOM

**Основные темы:**

- DOM.
- Поиск HTML-элементов.
- Изменение содержимого элементов.
- Создание HTML-элементов.
- Изменение атрибутов и классов.
- Удаление HTML-элементов.

На этом этапе необходимо связать JavaScript-логику с пользовательским интерфейсом.

## 6.1. Отображение задач

Необходимо реализовать отображение списка задач в браузере.

Для каждой задачи должен создаваться отдельный визуальный элемент.

Отображаемая информация должна соответствовать данным задачи.

## 6.2. Обновление интерфейса

После каждого изменения данных интерфейс должен обновляться.

Это касается следующих действий:

- Добавление задачи.
- Удаление задачи.
- Изменение статуса.
- Поиск.
- Фильтрация.
- Сортировка.

Пользователь не должен видеть устаревшую информацию.

## 6.3. Пустые состояния

Необходимо предусмотреть следующие ситуации:

- В приложении ещё нет задач.
- Поиск не дал результатов.
- В выбранной категории отсутствуют задачи.

Для каждой ситуации необходимо предусмотреть отдельное понятное сообщение.

## 6.4. Визуальное состояние задач

В зависимости от статуса необходимо менять внешний вид задачи.

Например:

- Выполненная задача должна визуально отличаться от активной.
- Название выполненной задачи должно иметь соответствующее оформление.
- Пользователь должен понимать, какие задачи ещё требуют выполнения.

**Результат этапа:** приложение отображает реальные данные и автоматически обновляет интерфейс.

# 7. Этап №4. Работа с событиями

**Основные темы:**

- События браузера.
- Обработчики событий.
- Работа с формами.
- Получение пользовательского ввода.
- Передача данных между элементами интерфейса и логикой приложения.

## 7.1. Добавление задач

Добавление должно происходить после отправки формы.

Пользователь должен иметь возможность добавить задачу удобным для себя способом, предусмотренным интерфейсом.

После успешного добавления:

- Новая задача появляется в списке.
- Обновляется статистика.
- Очищается поле ввода.
- Список отображается с учётом текущих настроек поиска и фильтрации.

## 7.2. Удаление задач

При нажатии на кнопку удаления соответствующая задача должна удаляться.

Удаление одной задачи не должно влиять на остальные.

## 7.3. Изменение статуса

Пользователь должен иметь возможность отмечать задачи выполненными и возвращать их в активное состояние.

Изменение статуса должно сразу отражаться в интерфейсе и статистике.

## 7.4. Поиск

Поиск должен выполняться непосредственно при вводе текста.

Пользователь не должен нажимать отдельную кнопку для запуска поиска.

## 7.5. Переключение фильтров

Переключение категории должно немедленно обновлять список отображаемых задач.

Выбранный фильтр должен сохраняться при выполнении других операций внутри приложения.

**Результат этапа:** всеми основными функциями приложения можно пользоваться через интерфейс.

# 8. Этап №5. Дополнительные возможности

**Основные темы:**

- Date.
- Math.
- JSON.
- localStorage.
- Работа с данными браузера.

## 8.1. Дата создания

Для каждой задачи должна сохраняться дата создания.

В интерфейсе необходимо отображать дату в понятном для пользователя формате.

## 8.2. Уникальные идентификаторы

Каждая задача должна получать уникальный идентификатор.

Нельзя допускать совпадения идентификаторов у разных задач.

## 8.3. Локальное сохранение

Необходимо реализовать сохранение списка задач в браузере.

Требования:

- При добавлении задачи изменения сохраняются.
- При удалении задачи изменения сохраняются.
- При изменении статуса изменения сохраняются.
- При перезагрузке страницы данные восстанавливаются.
- Если сохранённых данных нет, приложение должно корректно запускаться с пустым списком или начальными тестовыми данными.

## 8.4. Удаление выполненных задач

Добавить отдельную кнопку для удаления всех выполненных задач.

Перед удалением необходимо предусмотреть защиту от случайного нажатия.

После удаления должны корректно обновляться список и статистика.

**Результат этапа:** приложение сохраняет данные и не теряет их после перезагрузки страницы.

# 9. Дополнительные задания повышенной сложности

Эти функции не являются обязательными для сдачи основной работы.

## 9.1. Редактирование задачи

Добавить возможность изменить название уже созданной задачи.

Требования:

- Пользователь может перейти в режим редактирования.
- Может изменить название.
- Может сохранить изменения или отменить редактирование.
- Нельзя сохранять пустое название.
- Изменения должны сохраняться после перезагрузки страницы.

## 9.2. Приоритет задач

Добавить возможность указывать приоритет:

- Низкий.
- Средний.
- Высокий.

Добавить сортировку по приоритету.

## 9.3. Срок выполнения

Добавить возможность устанавливать дату, к которой задача должна быть выполнена.

Необходимо визуально выделять просроченные задачи.

## 9.4. Подтверждение удаления

При удалении задачи необходимо показывать дополнительное подтверждение действия.

## 9.5. Статистика выполнения

Добавить отображение процента выполненных задач.

Статистика должна автоматически пересчитываться при изменении списка.

# 10. Требования к качеству кода

При разработке необходимо соблюдать следующие правила:

1. Не размещать всю логику в одном файле или одной функции.
2. Не дублировать одинаковые участки кода без необходимости.
3. Использовать понятные названия переменных и функций.
4. Разделять работу с данными и отображение интерфейса.
5. Не хранить одинаковую информацию в нескольких местах без необходимости.
6. Корректно обрабатывать пустые значения.
7. Проверять пользовательский ввод.
8. Не допускать ошибок в консоли браузера.
9. Обеспечить корректную работу приложения при отсутствии задач.
10. Не использовать сторонние библиотеки и фреймворки.

Запрещается:

- Использовать React, Vue, Angular и другие фреймворки.
- Использовать jQuery.
- Подключать готовые библиотеки для управления задачами.
- Копировать готовые проекты.
- Использовать чужую реализацию бизнес-логики.
- Подменять JavaScript-логику статическими HTML-элементами.

- Самостоятельно выбирать оформление приложения.
